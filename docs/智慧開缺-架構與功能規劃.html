收容所智慧開缺

把「這週要開哪些班、需要幾個人」從收容所人員的腦袋裡搬到系統裡。志工招募不是收容所的額外工作，而是減壓的手段——前提是排班這件事本身不能再花人力。

01

先講一個必須先解決的矛盾

原本的構想是「依動物狀況調整志工需求」。方向對，但直接這樣做會反過來傷害招募——因為它和排班最基本的一條運作規律互相牴觸。

規律一 · 志工端 班表要提前一到兩週發布，才有人報得到

志工多半有正職或學業，要先看到班表才能安排自己的時間。太晚公布，班次不是沒人報，就是只剩少數幾位全職志工能來。

規律二 · 收容所端 動物狀況是天天在變的

今天有狗生病、明天有新入所、後天有送養活動。這些事件的時效以「天」計，不可能在兩週前就知道。

兩者直接相接的後果：班表會一直變動。志工報了名卻被通知取消或改期，幾次之後就不再相信這個系統，招募反而更難。而且基準需求其實是穩定的——貓舍每天要清、狗每天要放風，這跟今天有幾隻在治療關係不大。動物狀況真正影響的是少數個案。
02

解法：開缺分兩層

不要讓動物狀況去「調整」班表，而是讓它「疊加」在班表之上。兩層有各自的節奏、各自的發布時機，互不干擾。

表一 — 兩層的分工
　基準層增補層
需求來源班次範本＋各區固定照護量（清潔、放風、餵食）動物個案事件（醫療、新入所、送養活動）
發布時機提前 2 週，一次發布整期提前 2–3 天，隨事件發生
變動性發布後不動隨時可能新增
招募方式班表公開，志工自行報名搶班急召推播，指定條件的志工優先
需要動物資料嗎不需要需要（來自收容所 CRM）
佔全部人力約八成約兩成
一條不能破的規則：增補層只加，不減。

已經發布、已經有人報名的班次，不因為動物狀況變化而取消或改期。志工的信任一旦破了，後面所有招募都會變難，而那正是這整套系統想解決的問題。人力真的過剩時，讓多出來的志工做別的事，不要退掉他們的班。

這帶來一個很實際的好處：基準層完全不需要跟 CRM 整合。

八成的人力需求，靠班次範本和各區固定照護量就算得出來。也就是說第一階段可以完全獨立上線、獨立驗證，不必等兩套系統對接完成。整合是增補層才需要的東西，不是起跑條件。

03

系統架構

志工系統是一個獨立服務，不是 CRM 的一個頁面。它自己有資料庫、自己有登入、自己面對志工；跟 CRM 之間只有一條窄的、單向的資料通道，而且只有增補層會用到。

05

關於「智慧」：初期建議不要用 AI

這一節可能和「智慧開缺」的字面期待相反，但值得先講清楚，避免第一版就交出看起來聰明、實際上沒有根據的東西。

預測需要歷史樣本。目前系統裡累積的是 16 位志工、11 筆出勤紀錄——不足以支撐任何有意義的預測。若現在就接 AI，模型只能靠推測產生數字，而那些數字會以很有說服力的方式呈現出來。現有的缺工預測畫面就是這樣：在沒有資料的情況下，它會回傳「園區共 434 隻浪浪、下週缺 22 人次」這種寫死的示範值。

建議：第一階段用規則，不用模型。

「貓舍每日需 2 人 × 14 天 = 28 人次，目前報名 19，缺 9」——這種算法可解釋、可調整、人員一看就知道數字從哪來，錯了也知道去改哪個設定。累積三到六個月真實出勤之後，再談用歷史資料預測季節性與流失率，那時候 AI 才有東西可學。

06

部署與成本

主要有兩個問題要回答：多間收容所怎麼分攤成本，以及資料放哪裡才不會不見。第二個問題比第一個急，因為它有一種會安靜出錯的失敗方式。

多間收容所：各自架設是可行的

Google Cloud 的免費額度是以帳戶為單位計算的。不同的收容所是不同的機構、各自持有自己的 Google 帳戶，也就各自是獨立客戶，各自享有自己的免費額度——五間收容所、五個帳戶、五台免費的 e2-micro，完全站得住腳。（不成立的是同一個人開多個帳戶去累加額度，那違反使用條款。）

所以成本不是障礙。真正要衡量的是另一件事。

表四 — 集中一套 vs 各自架設
　集中一套（開發者維運）各收容所自行架設
機器費用一份各自的免費額度，同樣是零
部署更新改一次，部署一次改一次，要部署 N 次，由 N 個人執行

個資責任開發者保管所有收容所的志工個資各收容所自行保管自己的
對收容所的負擔零要有人顧一台機器
這是取捨，不是對錯，而決定性的問題只有一個：誰來維護？

只有一位技術人員時，集中一套省下的工遠多於分散。每間收容所都有能顧機器的人時，分散反而更健康——尤其是個資這一項：各自保管自己志工的資料，在個資法上是實質差別，不只是方便與否。

建議先不要決定。第一間跑順之後，維運實際花掉多少時間會是個具體數字，那時候再選才不是用猜的。

目前所有資料存在一個 SQLite 檔案裡（data/volunteers.db）。這個選擇本身沒問題，但它決定了能用哪一種機器。

一個看似可行、實際上會失效的做法：「重啟前先把資料匯出兩份」。Cloud Run 的重啟不是使用者能決定的時機——閒置回收、冷啟動、自動擴縮、平台維護都會觸發，而且都不會事先通知。沒有「重啟前」這個時間點可以掛勾，等發現的時候資料已經不在了。這個問題只能靠換資料層解決，不能靠匯出。選 e2-micro 則完全不會遇到。

備份

系統每天會自動產生一份資料庫快照，保留最近 14 份。但快照目前和資料庫在同一台機器上——機器壞掉就一起沒了。需要補的是異地：把快照定期上傳到雲端硬碟或物件儲存即可，這一步做完，備份才算真的成立。

附帶一提，雲端硬碟適合當備份的目的地，不適合當資料庫本身：它沒有交易、沒有並行控制、有 API 配額，撐不住多位志工同時簽到。

給主系統的資料

主系統只需要 CSV，這讓兩邊的介面單純很多——不需要即時介接，也不需要任何常駐的連線。目前的月報匯出已經是正確的形狀：園區名稱、統計月份、班次數、需求人數、已報名人數、缺工人數、缺工率、總服務時數。全部是統計數字，沒有任何一欄是個資。這個原則值得維持：給主系統的是數字，不是名冊。

唯一要改的是產出方式。現在必須有人記得去按匯出，而需要人記得的步驟遲早會被忘記，忘記的時候也不會有人發現。改成排程自動產出，這個問題就消失了。

Google Cloud 的免費方案條款會調整，正式規劃前請以官方 Free Tier 頁面為準。

07

第一階段要交出什麼

一句話：收容所人員花十分鐘設定各區照護量，系統產出未來兩週的完整班表草稿，確認後一次發布，志工在 LINE 收到通知開始報名。

這條路徑走通，「排班」這件事就從每期數小時的人工作業，變成十分鐘的確認。那才是「減輕收容所壓力」實際兌現的地方；其他功能再好，都不是這句話的答案。
