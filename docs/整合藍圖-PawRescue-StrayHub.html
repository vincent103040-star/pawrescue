架構分析 · 2026-08-24

PawRescue × StrayHub 整合藍圖

志工排班子系統要接上浪浪森友會 CRM 主後台。這份文件盤點兩邊實際的程式碼落差、按嚴重度排出會咬人的問題，並給出一套可以分階段落地的資料交換設計。

子系統：React 19 + Express + node:sqlite，約 2,480 行 server.ts 主後台：FastAPI + PostgreSQL(RLS) + Worker + MinIO，29 個 migration 依據：兩邊 repo 原始碼，非文件推測

先講結論

四個決策
不要做 共用資料庫，或讓任一邊直連對方的 DB

主後台的租戶隔離是 PostgreSQL FORCE ROW LEVEL SECURITY，靠每個交易開頭的 set_config('app.current_org_id', …) 生效。Node 端直連會整套繞過 RLS、樂觀鎖版本號、稽核寫入與授權到期判斷。

先擋住 子系統目前有十來個無授權檢查的 API

包含全志工名冊、出勤紀錄、LINE 推播與「自己核准自己升級」。整合會讓主後台的信任邊界延伸到這裡——這是 Phase 0，不是 backlog。

先定義 誰擁有哪塊資料，再談同步

兩邊都有 volunteer_applications，但一個是「入所志工資格審核」、一個是「單一班次報名」。名字撞在一起而語義相反，是整合最容易埋出資料錯亂的地方。

主鍵改成 StrayHub 的 user UUID

子系統目前以 email 當志工主鍵。跨系統穩定識別、改信箱、LINE 綁定、刪除傳播全都需要一個不會變的 ID。

兩邊的實際落差

現況對照

職責邊界

誰是真相來源

好消息是兩邊的核心領域幾乎不重疊，而且主後台在規格裡明確把排班排除在外（spec 001 FR-004：「不得擴大成完整班次排班系統」）。這代表子系統不是重複造輪子，而是補上主後台刻意不做的那塊。邊界因此可以切得很乾淨。

風險清冊

依整合前必須處理的順序

R1　子系統有一批完全沒有授權檢查的端點

已修復 · 2026-08-24

app.use('/api/admin', requireAdmin) 只蓋住 /api/admin/*。不在這個前綴、也沒有各自加檢查的端點，任何知道網址的人都能呼叫：

GET /api/volunteers → 全體志工名冊，含電話、Email、LINE ID GET /api/volunteers/profile → 任意 email 的完整個資 POST /api/volunteers/profile-extras → 改任意人的緊急聯絡人與頭像 POST /api/volunteers/log-hours → 以姓名替任意人加服務時數 GET /api/attendance → 全部出勤紀錄 POST /api/attendance/:id/check-out → 替任意簽到紀錄簽退並填時數 POST /api/promotions/:id/approve → 核准升級（可自審自核） POST /api/line/push /broadcast → 用收容所官方帳號對所有好友發訊 POST /api/ai/* → 消耗 Gemini 額度

另外預設管理員密碼是 '0000'（未設 ADMIN_PASSWORD 時 seed 進 DB）。

已完成：「預設拒絕」翻過來了——先 app.use('/api', requireAuth)，再明列真正的公開端點（登入、LINE webhook、健康檢查）。寫入類一律加 requireAdmin 或「只能操作自己」的擁有者檢查；/api/line/* 只允許管理員；/api/ai/* 加上速率限制。這件事跟整合無關也該做，但整合之後它的影響會從「這個小系統被亂改」升級成「CRM 信任了一個誰都能操作的服務」。

R2　同一個人，三套互不相通的鑰匙

整合阻斷

子系統用 email 當主鍵，主後台用 users.id（UUID）＋line_user_bindings.line_user_id。目前沒有任何欄位能把同一個人在兩邊對起來。用 email 當關聯鍵有三個具體問題：改信箱等於換人、Google 登入的 email 與志工申請時填的可能不同、以及 email 是個資，會被迫在每一次 API 呼叫裡傳來傳去。

要做的事：子系統 volunteers 加 strayhub_user_id（UUID，唯一）與 organization_id，並讓它成為對外唯一的識別。email 降級成一般聯絡欄位。首次配對用一次性綁定流程（志工在主後台的 LIFF 裡確認），不要用 email 自動比對——自動比對會在同名同姓或共用信箱時把兩個人接錯，而這種錯誤在稽核紀錄裡幾乎看不出來。

R3　LINE 通道會互相擋路

整合阻斷

兩邊各自有一套 LINE：子系統有自己的 Messaging API channel、Login channel 與 LIFF；主後台有 line_channel_* 設定、webhook 去重表、綁定表、rich menu context 與通知外送佇列。兩個硬限制會直接撞上：

  • 一個 Messaging channel 只能設定一個 webhook URL。兩邊不可能同時收同一個 channel 的事件，除非其中一邊當轉發器。
  • userId 只在同一個 Provider 底下才一致。不同 Provider 的兩套綁定資料無法互相對應——你在 HANDOFF 裡已經記過這件事。

再加上使用者體驗問題：志工要加兩個官方帳號、收兩份提醒、在兩個 rich menu 之間猜哪個能簽到。

要做的事：短期把兩個 channel 移到同一個 Provider，userId 立刻可對應，改動最小。目標態是單一 channel 由主後台持有：它已經有 webhook 去重（line_webhook_events.webhook_event_id 唯一）、綁定、以及帶重試與失敗清單的通知佇列——子系統改成呼叫主後台的通知 API，而不是自己打 LINE。順帶解掉一個現有 bug：子系統的通知偏好只有 /api/line/push 會檢查，broadcast 繞過它。

R4　租戶模型不對稱

高

主後台從資料庫層就假設「每一列都屬於某個組織」，子系統則假設「只有一間收容所」。一旦子系統開始快取來自主後台的租戶資料，它就變成一個租戶無感的副本；第二間收容所出現的那天，就是資料互相看見的那天。

要做的事：務實的選擇是一個收容所一套部署，ORGANIZATION_ID 放環境變數，服務帳號的 token 也只綁這一個組織——主後台側自然擋掉越權。同時現在就把 organization_id 欄位加進子系統各表（即使只有一個值），未來要走多租戶時不必動 schema，只要把常數換成請求範圍。反過來做（先多租戶再補隔離）的成本高一個數量級。

R5　主後台目前沒有機器對機器認證

高

OpenAPI 只有一種 bearerAuth，簽發途徑是帳密登入與 LIFF 交換，全部針對「人」。最容易的做法——幫子系統開一個管理員帳號、把帳密塞進 .env——會同時失去三件事：稽核裡分不出是人還是系統、無法只給部分權限、以及那組帳密會長期有效且散落在部署環境。

要做的事：加一組獨立的服務帳號（client credentials），細節見下一節。好消息是主後台已經留好接口：audit_records 的 CHECK 明確支援 actor_type='system' ＋ actor_reference（migration 0026），JWT 簽發也已抽象成 AccessTokenPort，不用重寫。

R6　時間表示法不一致

中

主後台存 UTC aware 時間並讓每個組織帶自己的 timezone；子系統存 '2026-08-24' 與 '09:00 - 12:00' 這類本地字串，時數是前端算完再送上來的 number。跨系統之後會出現三種錯：跨午夜的班次時數算錯、日期字串比較在時區邊界失準、以及「今天的班表」在兩邊指的不是同一天。

要做的事：凡是要跨邊界的時間，一律用 UTC ISO-8601 instant 傳輸，本地日期只保留給顯示。工時由伺服器從簽到／簽退 instant 計算，不接受客戶端送來的 hoursLogged——這同時修掉 R1 裡那個能任意灌時數的端點。

R7　SQLite 同步 I/O 會在同步作業時卡住現場

中

node:sqlite 的 DatabaseSync 是同步 API，直接跑在事件迴圈上。目前只有互動流量所以沒事，但加上定期同步、outbox 排空、批次 upsert 之後，一次幾百列的寫入會讓同一時間的簽到請求與 SSE 推送一起停住。data/volunteers.db 也還沒有備份。

要做的事：開 WAL（PRAGMA journal_mode=WAL）並設 busy_timeout；同步作業切成小批次（每批 ≤100 列）並用 setImmediate 讓出迴圈；備份就是定時複製一份 .db 檔到別的地方。若之後子系統要跟主後台一起上雲，改用同一台 Postgres 的獨立 database（不是同一個 schema）會一次解掉並行、備份與交易語義三件事。

R8　檔案儲存不對稱

中

子系統把簽退照片與頭像用 base64 收進來、寫本機磁碟，再用 express.static 公開；主後台用私有物件儲存加簽名 URL 與媒體淨化。若哪天簽退照片要進到動物時間軸，等於把一批本來就公開可讀的檔案接進一個嚴格控管的系統。

要做的事：照片不要跨系統搬。真的需要時，改成子系統向主後台要一組上傳用簽名 URL、直接上傳到物件儲存，子系統只留 media id。順帶把 30MB 的 base64 JSON 從請求路徑上拿掉。

三條資料流的契約

具體設計

A — 已核准志工名冊（主後台 → 子系統）

用整份快照輪詢，不要做增量游標。理由是規模：單一收容所的在籍志工是數百人量級，一份含 UUID、姓名、期效、角色旗標的 JSON 大約幾十 KB，五分鐘拉一次的成本遠低於維護游標的成本。而以 updated_at 當游標有個容易漏資料的陷阱——先開始、後提交的交易，其 updated_at 可能早於上一輪的游標值，那筆更新就永遠不會被拉到。真要做增量，得用 (updated_at, id) 複合游標加上一段重疊回看窗，或在主後台加一張單調遞增序號的變更表。

  • 主後台新增 GET /v1/integration/volunteer-roster，回傳 user_id、display_name、membership.status、valid_from、expires_at、access_version。不含電話與 Email。
  • 回應帶 ETag；子系統帶 If-None-Match，沒變動就是 304，實際傳輸量趨近於零。
  • 子系統把快照寫進本地表並記下 synced_at。簽到時只讀本地表，不做同步呼叫——現場網路不該擋住簽到。
  • 即時性由流 C 補足，輪詢只是防止漏接的保底。

B — 到勤事實（子系統 → 主後台）

出勤是只增不改的事實，天然適合 at-least-once ＋冪等接收，這是三條流裡最安全的一條。

  • 每筆簽到／簽退寫進本地 integration_outbox，帶一個生成即固定的 event_id（UUID）。
  • 背景排空，指數退避；主後台以 (organization_id, event_id) 唯一索引去重，重送必然安全。
  • Payload 只帶 strayhub_user_id、UTC instant、班次代碼、驗證方式（self／staff）與是否通過定位驗證。不要送 GPS 座標——主後台不需要，而座標是敏感資料。
  • 主後台側以 actor_type='system'、actor_reference='pawrescue' 寫稽核，之後查得出每一筆到勤是哪個系統、哪個版本寫進來的。

C — 撤銷與到期（主後台 → 子系統）

這條是安全關鍵：資格被撤銷的人必須立刻進不了現場，不能等下一輪輪詢。

  • 主後台 Worker 在 expire_access 與撤銷流程後，對已註冊的整合端點送 webhook。
  • 簽章用 HMAC-SHA256 涵蓋「時間戳＋原始 body」，子系統驗簽並拒收 5 分鐘外的時間戳（重放保護），事件 id 另做去重。
  • 子系統收到就地標記失效，不需等待下次快照。
  • 送不到要進主後台自己的重試佇列——它已經有這個機制。

整合認證

機器不是人
  • 獨立的服務帳號憑證。新增一張 integration_clients：client_id、Argon2 雜湊後的 secret、organization_id、scope 清單、狀態。沿用現成的 PasswordHasherPort。
  • 短效 token。POST /v1/integration/token 走 client credentials，簽出 900 秒的 RS256 JWT，claim 帶 actor_type=system、client_id、organization_id、scope。不要讓機器走人類的 refresh token 輪替流程——那套設計是為了偵測 token 被竊後的家族撤銷，語義不適用，混用反而會讓兩邊的失效邏輯互相干擾。
  • 最小 scope。子系統只需要 roster:read 與 attendance:write 兩個。名冊唯讀的服務帳號即使外洩，也拿不到動物、醫療與回報資料。
  • 組織綁定。token 只綁一個 organization_id，套用一般租戶範圍而非 platform scope——RLS 會自動兜底。
  • 金鑰保管。放 Secret Manager 或部署平台的密鑰儲存，不要進 .env.local、不要進 git，並排一個輪替流程（新舊 secret 並存一段時間再停用舊的）。
  • 可追蹤。每次呼叫帶 X-Operation-Id，主後台寫進 audit_records.operation_id，一筆簽到就能從志工手機一路追到 CRM。

主後台掛掉時，現場還能做什麼

降級規則

「全部擋住」和「全部放行」都是錯的答案。按情境分開決定，並且把降級狀態顯示給現場人員看——他們需要知道自己正在用的是快取。

主後台不可用，本地名冊新鮮（< 24h）放行照常簽到，出勤進 outbox簽到只需要「這個人今天有資格」，24 小時內的快照足以回答
主後台不可用，名冊過期（> 24h）放行但標記簽到可用，紀錄標為 unverified，管理端顯示待補驗擋住現場作業的代價，高於事後補驗幾筆紀錄

效率

按實際規模
  • 不要在使用者請求路徑上同步呼叫另一個系統。簽到讀本地、寫本地、回應，跨系統的事交給背景。若真有非同步不可的情形，一律加 AbortSignal.timeout()（3 秒）與連續失敗後跳開的斷路器——Node 的 fetch 預設不會逾時，一個掛住的 CRM 會拖垮整個 Express 程序。
  • ETag 比增量游標划算。以你的資料量，304 回應的成本接近零，而且沒有游標會漏資料的風險。
  • 批次而非逐筆。outbox 一次送 50–100 筆事件，減少往返與 TLS 交握。
  • SSE 已經在了。子系統既有的 /api/events 可以直接用來把「名冊已更新」推給正開著的管理端，不必為此加輪詢。
  • 批次寫入讓出事件迴圈。見 R7；這是唯一會實際影響到現場體感的效能問題。

個資與法遵

資料流動就要重新盤點
  • 不要對稱複製。子系統握有電話、Email、緊急聯絡人、照片、GPS 與評分；主後台刻意只留 display_name ＋ LINE 綁定。整合的正確方向是讓每一項個資只有一個家，交換的是 ID 與最小必要欄位。
  • 位置資料要特別對待。簽到的 GPS 座標留在子系統，跨界只送「是否通過定位驗證」的布林值。
  • 刪除要會傳播。主後台已經有期效與撤銷的完整生命週期；子系統目前是永久保存。志工撤回同意或資格終止時，子系統要能真的刪除或去識別化，不是只加一個過濾條件。這需要一條刪除事件，而不只是名冊快照裡少一列——快照少一列跟「同步失敗」長得一模一樣。
  • 個資法的告知範圍。志工當初同意的蒐集目的是排班；資料要送進 CRM 屬於利用範圍的變更，蒐集聲明與同意流程需要更新。這件事在動工前確認，比事後補容易得多。
  • 保留期限。出勤與工時有服務證明的用途，需要長期保存；SOP 測驗答案、AI 評估文字、簽退照片則不需要。分別訂期限並實際執行清理。

契約治理

避免無聲漂移
  • 主後台已經把 OpenAPI 當唯一真相並產生 TS 型別（@strayhub/contracts，附 check-generated 檢查）。子系統直接吃這包產生的型別，不要手寫 fetch——兩邊 CI 都跑檢查，契約一漂移就紅燈。
  • 注意一個不對稱：主後台的 Pydantic model 幾乎都設 extra="forbid"。子系統多送一個欄位會被整個請求拒絕；反過來，子系統要能容忍回應裡出現沒見過的欄位。這條寫進整合的程式碼規範裡。
  • 整合端點放在 /v1/integration/*，跟人類用的 API 分開，之後才有機會獨立演進與獨立限流。
  • 只做加法式變更：新增選填欄位可以，改語義、改必填、刪欄位都要新版本路徑。
  • 接收端一律做契約測試（主後台側已有 contract pytest marker，直接沿用），而不是靠整合環境手測。

落地順序

每階段都有可驗收的產出

  1. 止血：子系統的授權基線　已完成

    預設拒絕的中介層、公開端點白名單、寫入端點的擁有者檢查、移除預設密碼 0000、/api/line/* 限管理員、AI 端點加速率限制、開 WAL 與定時備份。

    這階段完全不碰整合，但它是後面所有階段的前提——在一個誰都能改資料的系統上談資料交換沒有意義。

    驗收通過（PR #1，2026-08-24 合併）：46 個受保護端點未帶 token 全部回 401，11 個白名單端點照常運作，2 種偽造登入被拒。另外補掉一個更嚴重的洞——Google 登入端點原本完全不驗 token，帶任何 email 就能取得該志工的 session。真實 Google 與 LINE 登入已實測可用；簽退時數以測試前的自動備份比對，確認剛好記一次。留下 npm run check:security（59 項）可隨時重跑，該腳本本身也以刻意注入的漏洞驗證過會紅燈。

  2. 對齊：身分與邊界

    子系統加 strayhub_user_id、organization_id；volunteer_applications 改名 shift_signups；跨界時間統一 UTC instant；工時改由伺服器計算；兩個 LINE channel 移到同一個 Provider。

    驗收：可以人工把一位志工在兩邊的紀錄對起來，且 LINE userId 一致。

  3. 單向唯讀：名冊同步

    主後台新增服務帳號與 GET /v1/integration/volunteer-roster；子系統做快照拉取與本地快取，簽到改讀快取。這一階段不寫回任何東西——先讓資料流動起來，風險最低，而且能真實驗證身分對映對不對。

    驗收：在主後台核准一位新志工，五分鐘內他能在現場完成簽到。

  4. 寫回與即時失效

    子系統 outbox ＋ 到勤事件推送；主後台冪等接收並寫 actor_type='system' 稽核；撤銷／到期 webhook 上線；降級規則與積壓監看落到管理端畫面上。

    驗收：斷開主後台 30 分鐘，現場簽到照常，恢復後出勤一筆不漏也不重複；撤銷一位志工後他當場被擋下。
